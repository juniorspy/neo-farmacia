## Health board de flota

  healthcheck de Dokploy.
- **`GET /api/v1/admin/fleet-health` (super-admin)**: una sola llamada
  devuelve, por farmacia:
  - **WhatsApp**: conexiones con estado VIVO (consulta a Evolution vía
    `syncConnectionLiveState`, persiste drift + invalida el cache del

    `connection.service.ts` para DRY).
  - **Catálogo**: conteo real del índice (Meili `/stats`) + `isIndexing` +
    último sync y último error desde `Store.catalog_sync`.
  - **Último mensaje** procesado (timestamp, dirección, sender).
  - **Voz hoy**: total + perdidas (medianoche en el timezone de la farmacia).
  - **Errores recientes**: `last_error` del job de provisioning (se limpia en
    retry/éxito) + error del último sync de catálogo.

## Deuda de observabilidad pagada (gap de la sesión 2026-06-06)

1. **Éxito silencioso de Meilisearch resuelto**: `upsertDocuments` ahora
   devuelve el `taskUid` y el sync espera el resultado con `waitForTask`
   (las tasks corren en orden de uid → esperar la última cubre todo el
   batch). Task fallida = sync fallido, registrado y visible en el board.
2. **`lastSyncByStore` (in-memory) eliminado**: el cursor de sync incremental
   ahora es `Store.catalog_sync.last_synced_at` (+ `last_error`). Sobrevive
   reinicios — un redeploy ya NO fuerza full rebuild por farmacia — y es la
   fuente del board. El timestamp se captura ANTES de la query a Odoo: el
   solape re-sincroniza algunos productos (upsert idempotente) en vez de
   perder ediciones hechas mid-sync.
3. **`GET /health`** descrito arriba.

## Decisiones de diseño

- El estado WhatsApp del board es **vivo** (N llamadas a Evolution con
  timeout 5s, `Promise.all`, nunca lanza) — a escala actual (pocas farmacias,
  1-3 conexiones c/u) el costo es trivial y el dato es el que importa.
- "Errores recientes" agrega las señales persistidas que ya existen
  (provisioning + sync); no se creó colección de error-log nueva — candidato
  futuro si el board se queda corto.
- `requireSuperAdmin` exportado de `admin.routes.ts` y reutilizado.

## Schemas en las 56 rutas — los docs viven en el código

Directiva del usuario: "poner las docs a la parte con el código para no
dejarlo atrás". Pasada completa por los 16 archivos de rutas:

- **Cada ruta** ganó `schema` con `summary` + descripción (auth requerida,
  comportamiento, shape de respuesta como texto) + validación de
  `body`/`params`/`querystring` donde aplica. **Cobertura: 56/56** (el
  smoke-boot ahora la verifica e imprime las rutas sin documentar).
- **Decisiones de seguridad del cambio** (cero roturas a consumidores):
  - SIN `response` schemas: en Fastify no son docs — recortan campos no
    declarados al serializar. Los shapes van como texto; contratos enforced
    vendrán ruta a ruta cuando se quiera.
  - SIN `additionalProperties: false`: campos extra pasan, nada se recorta
    (Ajv de Fastify trae `removeAdditional`).
  - SIN body schema donde el caller postea sin body: reject de ítem (el
    dashboard hace `api.post(url)` a secas — verificado), transcript y
    providers/report del worker, rutas del cliente de voz (token `?t=`).
  - Webhook de Evolution: solo docs, sin validación — nunca rechazar un
    evento entrante por schema.
  - Checks manuales de los handlers se conservan (con el schema delante no
    se disparan; el shape de los 400 existentes no cambia).
- Los `required` de los schemas se derivaron del código real de cada handler
  (mismos campos que ya producían 400 manual).

## Hardening de auth — cierre de endpoints abiertos (preocupación del usuario)

Pregunta del usuario: "¿cualquiera podría escribir a mi sistema usando el API?"
Respuesta honesta: SÍ, había agujeros reales. Inventario y cierre:

| Agujero | Gravedad | Fix |
|---|---|---|
| `JWT_SECRET` con default público en el repo | 🔴🔴 forjar token super-admin | Boot guard: en producción lanza si falta o es el default |
| `/api/v1/commands` fail-OPEN si `N8N_API_KEY` vacía | 🔴 despachar/cancelar pedidos de cualquier farmacia | Fail closed + boot guard exige la key en prod |
| `POST /api/v1/orders/update` (legacy) sin auth | 🔴 crear pedidos/partners en el Odoo principal | `Bearer N8N_API_KEY` |
| `POST /api/v1/users/lookup` sin auth | 🔴 contaminar usuarios en Mongo | `Bearer N8N_API_KEY` |
| `PUT /chats/:chatId/mode` sin auth | 🔴 silenciar el bot chat por chat | JWT del dashboard O bearer n8n (dual) |
| `products/search`, `products/:id` sin auth | 🟡 leer catálogo | `Bearer N8N_API_KEY` |

- Helper compartido `shared/n8n-auth.ts` (`n8nBearerOk` timing-safe que falla
  cerrado + `makeN8nGuard`); commands y voice-calls migrados al mismo (DRY,
  se eliminó el `bearerOk` duplicado de voice).
- Modo dev sin fricción: sin `N8N_API_KEY` configurada FUERA de producción,
  las rutas n8n siguen abiertas (el guard de boot hace imposible ese estado
  en prod).
- `DOCS_ENABLED=false` disponible para ocultar /docs en prod si se quiere.
- Guards verificados ejecutando `loadConfig()` con `NODE_ENV=production`:
  ambos lanzan con el mensaje correcto.

**⚠️ Acción requerida antes del próximo deploy (Dokploy env):**
1. `JWT_SECRET` seteado con valor aleatorio fuerte (si falta, el API NO bootea
   — a propósito).
2. `N8N_API_KEY` seteada (ídem).
3. Los nodos n8n que llamen `products/search`, `orders/update`, `users/lookup`
   o el modo handover ahora necesitan header `Authorization: Bearer <N8N_API_KEY>`
   (igual que /commands).

**Doc de seguridad creado**: `docs/architecture/security.md` — doble propósito
(one-pager para el IT de la farmacia + checklist interno de postura con estado
real ✅/⚠️/⏳). Captura: qué PII guardamos (nombre/teléfono/dirección/chat_id —

## Tienda online plug-and-play — código completo

Frente elegido para seguir desarrollo. Decisión de arquitectura tomada con el
usuario (2 opciones presentadas con trade-offs):

- **Motor: storefront propio en Next.js sobre nuestra API** — NO el
  website/eCommerce nativo de Odoo. Razón: el hosting multi-DB de Odoo website
  (dominio→DB por host) es frágil, el branding es pobre, y la tienda quedaría
  desconectada del buzón unificado de pedidos. El storefront propio reusa
  ~80% (búsqueda Meili, pipeline de pedidos, patrón de página pública del
  `/call`) y mantiene "contratos solo vía API".
- **Checkout: pago contra entrega / en caja** (regla #12, sin pasarela, sin PCI).
- **Lo potente**: el pedido web crea un `sale.order` con `client_order_ref=web`
  en la MISMA DB Odoo de la farmacia → aparece en `/orders` junto a los de
  WhatsApp y voz. Un solo buzón para todos los canales.

### Backend — módulo `storefront` (4 rutas públicas, sin JWT)
- `GET /storefront/:storeId` (info), `GET .../products` (Meili), `GET
  .../products/:id`, `POST .../orders`.
- Seguridad del POST público: precios SIEMPRE leídos del catálogo en el
  servidor (el cliente nunca fija precio); valida `sale_ok`+existencia;
  rate limit por IP (5/10min en Redis); cap de qty por línea.
- `createSaleOrderScoped` extendido con opts `{clientOrderRef, note}`
  (backward-compatible) — el note lleva los datos de entrega.
- El cliente se persiste en `User` con `chat_id=web:<phone>` (dedup con
  WhatsApp queda para después).

### Frontend — `/store/[storeId]` (público, fuera del auth group)
- `lib/storefront.ts`: cliente fetch sin token + carrito en localStorage.
- Catálogo: header de farmacia, búsqueda con debounce, grid responsive,
  add-to-cart con stepper, drawer de carrito, barra sticky móvil.
- Checkout: resumen + form (nombre/tel/dirección/nota) → POST → pantalla de
  confirmación.

### Imágenes — hallazgo (mejor de lo esperado)
El dashboard YA sirve ~110 imágenes de producto en `public/products/<code>.jpg`
y `odooProductToDoc` setea `image_url=/products/<code>.jpg` (quitando el prefijo
`CAROL-`). Resultado: **store_leo (catálogo CAROL) muestra imágenes reales en la
tienda sin trabajo extra**. La caveat de "imágenes pendientes" se reduce: solo
falta para catálogos importados con SKUs que no matchean esos archivos (ej. los
17k de `pharmacy_inventory`, o productos sin foto). El `ProductImage` degrada a
placeholder cuando no hay match — robusto en ambos casos.

### Mi Tienda + QR (panel de la farmacia)
Página `/tienda` (sidebar, junto a Mi Agente): la farmacia ve el enlace de su
tienda (`<origin>/store/<storeId>`), un **QR descargable** para imprimir/pegar
en el mostrador, copiar enlace, abrir y compartir. Dep nueva: `qrcode.react`
(client-side, sin llamada externa). El URL se arma con `window.location.origin`
— la tienda la sirve la misma app, sin env nueva.
